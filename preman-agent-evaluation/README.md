# PreMan agent evaluation coding assignment starter

Build the **evaluation system**, not this supplied target agent. The full brief is in `Candidate Assignment.docx`, included in this kit.

## Start the target

Requires Python 3.10 or later. The target uses only the Python standard library.

```sh
python3 target_server.py --port 8765
```

In another terminal:

```sh
python3 -m unittest discover -s tests -v
```

These tests verify the supplied target. Your submission must separately test **your evaluator**. Read `README_PROTOCOL.md` for endpoint contracts and responses. The default fixture directory is `fixtures/` beside the target script.

## You implement

- External scenario validation and loading from `scenarios.json`.
- Isolated sessions, multi-turn execution, timeouts, bounded concurrency, repeat counts, and cleanup.
- Chat and audio adapters that actually call the target; the audio adapter sends WAV bytes.
- Configurable business-state and confirmation-policy checks, with evidence-based PASS, FAIL, ERROR, and INCONCLUSIVE results.
- Audio metrics computed from the returned event timeline, with unavailable telemetry handled explicitly.
- Baseline-versus-faulty comparison, machine-readable JSON, and an HTML or Markdown report with linked trace and audio artifacts.
- Persistent run manifests and evidence, plus an offline command that regrades saved runs with the target stopped.
- At least two additional compatible scenarios: one chat and one audio. Leave the eight supplied definitions intact.
- Your own automated evaluator tests and setup/run/test/replay instructions.

Run each scenario against `baseline` and `faulty`. Results must follow observed state/events and the scenario's expectations, not a lookup keyed by scenario ID, fixture name, or variant.

## Scenario format

`scenarios.json` contains `schema_version` and a `scenarios` list. Each case has:

- `id`: stable report label, never a grading oracle.
- `fixture`: supplied initial environment/behavior family sent when creating the target session.
- `modality`: `chat` or `audio`.
- `turn_timeout_ms`: response deadline for each turn.
- `turns`: ordered `text`, `audio`, or `interrupt` actions. Audio paths are relative to this starter directory.
- `expect`: declarative checks; these remain in the evaluator and must not be sent to the target.

Supported expectation fields:

- `booking.count`: total persisted bookings in the isolated session. If greater than zero, every booking must match `customer_id` and `starts_at` when supplied. Booking IDs are generated by the target and are not prescribed.
- `address`: exact expected final address.
- `no_write_without_confirmation`: all address writes require a preceding explicit confirmation in the same session; use authoritative audit records.
- `max_first_audio_playback_ms`: every audio turn must have a measurable value within the limit; missing required telemetry must not silently pass.
- `max_interruption_stop_ms`: each requested interruption needs a scoped, complete metric within the limit.

For cases without an expectation field, do not invent that check. Treat unsupported expectation types as a scenario-validation error.

## Audio boundaries

The WAV inputs contain synthetic spoken English, mono, 16 kHz, 16-bit PCM. `fixtures/audio_manifest.json` maps the accepted files to scripted utterances. The target matches input by SHA-256 and returns prerecorded speech. It does not run speech recognition or synthesis during a test.

The timestamps use a **simulated fixture clock**. They are not actual transport or playback measurements. An `interrupt` request is a scripted event injection, not a test of concurrent live barge-in. Returned WAVs provide actual audio bytes; simulated events define the measurement fixture. Do not infer the simulated timeline from WAV duration.

Compute:

- first playback latency = first audio played minus user utterance end;
- interruption latency = playback stopped minus interrupting user speech start.

Scope pairs to the same session/turn/response and clock domain. Keep measured runner duration separate. Missing events produce unavailable metrics, not zero. Document what a real streaming/provider adapter would need to observe.

## Submission

Timebox: two to three working days, maximum 24 hours of implementation effort, followed by a 60-minute code walkthrough. Finishing earlier is fine; stop at the cap. Submit code, evaluator tests, reproducible commands, a generated report with artifacts, and a short README including time spent, tradeoffs, incomplete work, and AI-tool use. AI coding tools are allowed; you must understand and modify your code in the walkthrough.

You may add scenarios, but do not modify the eight original definitions, supplied target, fixtures, or target tests to make your evaluator pass. No paid credentials, GPU, production data, or elaborate UI is required. The target binds to localhost by default and is for this exercise only.

## Suggested build plan

- Day 1: scenario loading, isolated execution, chat adapters, state/policy grading, core tests, and basic results.
- Day 2: audio integration and metric tests, baseline comparison, and persistent evidence.
- Day 3 if needed: reliability and integration checks, offline regrading, added coverage, and documentation.

The same acceptance criteria apply to two- and three-day submissions. Demonstrate at least ten scenarios against both variants with two repeats (at least 40 attempts); compare concurrency 1 and 3. Add at least one chat case and one audio case using supported fixtures and existing WAVs. Exercise new conversation paths or expectation combinations, not renamed copies. Document expected outcomes for both variants. The supplied target rejects arbitrary new recordings.

Each saved run needs a unique ID, UTC start time, evaluator Git commit or source archive hash, target configuration, scenario file hash and definitions, concurrency, repeats, and relative artifact paths. Preserve raw responses and events, authoritative state or state-read errors, timeout evidence, and response audio.

Offline regrading must reproduce original check outcomes with unchanged expectations and without contacting the target. Support changing expectations or thresholds; changing conversation inputs requires a new target run. Save replay output separately, reference the original run, preserve artifacts, and distinguish replay duration from original agent timing. Missing evidence must remain explicit.
